# 论文报告写作 Agent Web 应用设计文档

## 1. 项目概述

本项目是一个面向课程设计报告、本科毕业论文、开题报告等场景的 Web 写作辅助应用。系统的目标不是一次性替用户生成完整论文，而是通过结构化信息收集、大纲规划、章节关系建模、逐章生成和全文一致性检查，帮助用户生成一份前后连贯、结构完整、便于继续修改的初稿。

系统重点解决以下问题：

- 用户不知道如何从题目拆出合理大纲。
- 生成的章节之间相互割裂，前后缺少承接。
- 同一项目背景、技术路线、系统功能在不同章节中表述不一致。
- 课程设计报告和本科论文格式要求不同，用户难以稳定控制文体。
- 导师意见、学校模板、项目代码或实验数据难以融入正文。

第一版产品定位为“初稿编排系统”。它应当帮助用户把论文或报告从零推进到可修改的完整初稿，而不是承诺直接生成最终定稿。

## 2. 目标用户

主要用户：

- 需要完成课程设计报告的本科生。
- 需要完成本科毕业论文初稿的本科生。
- 有项目代码、实验数据或系统设计材料，但不擅长整理成报告的学生。

次要用户：

- 指导学生写课程报告或论文的教师。
- 需要批量生成规范化项目文档的培训机构或课程团队。

## 3. 核心使用场景

### 3.1 课程设计报告初稿

用户输入课程名称、报告题目、技术栈、功能模块、实验环境和学校要求。系统生成课程设计报告大纲，并按“需求分析、概要设计、详细设计、实现过程、测试结果、总结”等章节逐章生成初稿。

### 3.2 本科论文初稿

用户输入论文题目、专业方向、研究背景、研究目标、技术路线、创新点和字数要求。系统生成本科论文大纲，并建立章节之间的承接关系，再逐章生成正文。

### 3.3 根据导师意见修改

用户录入导师意见，如“第二章理论基础太少”“第五章测试用例不够”“绪论研究意义太空”。系统将意见绑定到对应章节，并生成修改建议或直接重写相关段落。

### 3.4 从项目代码生成系统实现章节

用户上传或粘贴项目目录、核心代码、数据库表结构、接口说明。系统根据代码材料辅助生成系统设计、模块实现和测试分析章节。

## 4. 产品原则

### 4.1 以结构为中心

系统优先建立论文结构、大纲关系和章节目标，然后再生成正文。任何正文生成都必须依赖全局项目信息和当前章节关系。

### 4.2 以用户事实为来源

系统不能主动编造实验结果、功能模块、参考文献或技术细节。缺失信息应提示用户补充，或在草稿中使用可编辑占位说明。

### 4.3 逐章生成

系统不默认一次性生成全文。每章生成完成后，系统自动生成本章摘要、关键结论和对后续章节的影响，供后续生成使用。

### 4.4 初稿优先

第一版重点是生成可修改的完整初稿，不追求自动排版、查重检测、深度学术研究等高级能力。

### 4.5 可追踪修改

用户需要能够看到每个章节的生成依据、章节目标、上下文来源和最近修改记录。

## 5. 信息架构

应用主要包含以下模块：

- 项目管理
- 关键信息填写
- 大纲生成与编辑
- 章节关系建模
- 章节写作
- 全文一致性检查
- 导出与归档

项目中的核心信息包括：

- 项目基础信息
- 项目上下文
- 大纲结构
- 章节关系
- 章节草稿
- 章节摘要
- 导师意见
- 参考资料
- 导出记录

## 6. 页面流程

### 6.1 首页 / 项目列表页

功能：

- 展示用户已有写作项目。
- 新建项目。
- 继续最近项目。
- 查看项目状态，如“待补充信息”“已生成大纲”“正在写作”“可导出”。

主要操作：

- 新建项目
- 打开项目
- 删除项目
- 复制项目

页面核心字段：

- 项目标题
- 项目类型
- 创建时间
- 最近更新时间
- 当前进度
- 已完成章节数

### 6.2 项目创建页

功能：

- 选择写作类型。
- 填写项目基础信息。
- 设置字数和格式要求。

表单字段：

- 写作类型：课程设计报告 / 本科论文 / 开题报告
- 标题
- 专业或课程名称
- 学校或学院
- 目标字数
- 语言：中文 / 英文
- 是否有固定模板
- 截止日期

用户提交后，系统创建项目并进入项目信息填写页。

### 6.3 项目信息填写页

功能：

- 收集生成大纲和正文所需的核心事实。
- 通过分组表单降低填写压力。
- 标记信息完整度。

表单分区：

#### 基础背景

- 项目背景
- 要解决的问题
- 研究或设计目标
- 应用场景
- 目标用户

#### 技术与方法

- 使用技术栈
- 研究方法或开发方法
- 系统架构
- 开发环境
- 数据来源

#### 功能与内容

- 主要功能模块
- 核心流程
- 数据库或数据结构说明
- 实验或测试内容
- 已完成成果

#### 写作要求

- 学校格式要求
- 教师额外要求
- 章节固定要求
- 参考文献数量要求
- 风格偏好

页面操作：

- 保存信息
- AI 整理为项目 Brief
- 生成大纲

### 6.4 Project Brief 确认页

功能：

- 将用户填写的零散信息整理成统一的项目说明。
- 让用户确认后作为后续生成的事实来源。

Project Brief 包含：

- 题目解释
- 项目背景
- 核心问题
- 目标与意义
- 技术路线
- 功能模块
- 预期成果
- 写作边界
- 不确定或缺失信息

页面操作：

- 接受 Brief
- 继续编辑
- 标记某些内容为“不可更改事实”

### 6.5 大纲生成与编辑页

功能：

- 根据项目类型和 Project Brief 生成大纲。
- 用户可以编辑章节标题、顺序和层级。
- 支持课程设计报告和本科论文两种默认模板。

大纲元素：

- 一级章节
- 二级小节
- 章节目标
- 建议字数
- 章节状态

操作：

- 生成大纲
- 重新生成大纲
- 添加章节
- 删除章节
- 拖拽排序
- 锁定章节
- 确认大纲

课程设计报告默认大纲：

1. 绪论或项目概述
2. 需求分析
3. 系统概要设计
4. 系统详细设计
5. 系统实现
6. 系统测试
7. 总结
8. 参考文献

本科论文默认大纲：

1. 绪论
2. 相关理论与技术基础
3. 需求分析或研究方案
4. 系统设计或模型设计
5. 系统实现或实验分析
6. 测试与结果分析
7. 总结与展望
8. 参考文献

### 6.6 章节关系页

功能：

- 建立章节之间的前后承接关系。
- 明确每章的写作目的、输入信息和输出结论。
- 这是保证全文连贯性的关键页面。

每章包含：

- 章节标题
- 本章目的
- 承接上一章内容
- 引出下一章内容
- 本章必须说明的问题
- 本章依赖的项目事实
- 本章输出的关键结论
- 需要避免的重复内容
- 建议字数

页面展示形式：

- 左侧：章节列表
- 中间：当前章节关系编辑区
- 右侧：上下文预览，包括上一章摘要、下一章目标、项目 Brief 摘要

页面操作：

- AI 生成章节关系
- 单章重新生成关系
- 手动编辑关系
- 锁定关系
- 进入章节写作

### 6.7 章节写作页

功能：

- 按章节生成、编辑和重写正文。
- 每次生成都使用全局 Brief、大纲、章节关系、前文摘要和用户材料。

页面结构：

- 左侧：大纲导航
- 中间：章节编辑器
- 右侧：生成控制面板

生成控制项：

- 生成整章
- 生成小节
- 续写
- 重写选中段落
- 降低 AI 味
- 增强学术表达
- 增加工程细节
- 压缩内容
- 扩写内容

上下文面板显示：

- Project Brief
- 当前章节目的
- 上一章摘要
- 本章关键点
- 下一章承接方向
- 相关用户材料

章节生成后，系统自动生成：

- 本章摘要
- 本章关键结论
- 已使用项目信息
- 对后续章节的影响

### 6.8 全文一致性检查页

功能：

- 在所有章节生成后，检查前后逻辑和术语一致性。

检查项：

- 标题与正文是否匹配
- 章节之间是否有跳跃
- 术语是否统一
- 技术栈表述是否一致
- 功能模块是否前后对应
- 摘要、绪论和总结是否呼应
- 是否存在明显重复段落
- 是否出现用户未提供的事实
- 是否有章节过短或过长

输出形式：

- 问题列表
- 影响章节
- 修改建议
- 一键应用修改
- 手动编辑入口

### 6.9 导出页

功能：

- 预览全文。
- 选择导出格式。
- 应用模板。

导出格式：

- Markdown
- Word `.docx`
- PDF
- LaTeX，可放到后续版本

导出设置：

- 是否生成目录
- 是否包含封面
- 是否包含参考文献
- 标题编号样式
- 图片和表格编号
- 学校模板

## 7. 关键用户流程

### 7.1 从零生成本科论文初稿

1. 用户创建项目，选择“本科论文”。
2. 用户填写题目、专业、字数和学校要求。
3. 用户填写项目背景、目标、技术路线和功能模块。
4. 系统整理 Project Brief。
5. 用户确认 Brief。
6. 系统生成论文大纲。
7. 用户编辑并确认大纲。
8. 系统生成章节关系。
9. 用户确认章节关系。
10. 用户逐章生成正文。
11. 每章生成后系统保存章节摘要。
12. 全部章节完成后，系统执行一致性检查。
13. 用户根据建议修改。
14. 导出 Word 或 Markdown。

### 7.2 修改已有章节

1. 用户进入章节写作页。
2. 选择需要修改的章节或段落。
3. 输入修改要求，如“更像本科论文”“增加系统测试细节”。
4. 系统读取当前章节、章节关系、前后摘要和 Project Brief。
5. 系统生成修改版本。
6. 用户选择应用或继续调整。

### 7.3 根据导师意见修改

1. 用户录入导师意见。
2. 系统将意见关联到章节。
3. 系统生成修改计划。
4. 用户确认修改范围。
5. 系统逐章修改并记录变更。

## 8. AI 生成策略

### 8.1 分阶段生成

系统采用分阶段生成：

1. 信息整理
2. Project Brief
3. 大纲
4. 章节关系
5. 章节正文
6. 章节摘要
7. 全文一致性检查
8. 润色与导出

### 8.2 上下文压缩

后续章节不直接依赖全部前文正文，而是依赖：

- Project Brief
- 完整大纲
- 已完成章节摘要
- 上一章结尾摘要
- 当前章节关系
- 用户指定材料

这样可以减少上下文过长导致的遗忘和跑题。

### 8.3 事实约束

Prompt 中必须包含以下约束：

- 不得编造用户未提供的实验结果。
- 不得编造真实参考文献。
- 不确定信息使用“待补充”标记。
- 技术、功能、数据必须与 Project Brief 保持一致。
- 输出应符合当前写作类型。

## 9. MVP 范围

第一版必须包含：

- 项目创建
- 关键信息填写
- Project Brief 生成
- 大纲生成与编辑
- 章节关系生成与编辑
- 逐章生成正文
- 章节摘要生成
- 全文一致性检查
- Markdown 导出
- Word 导出

第一版暂不包含：

- 自动查重
- 自动真实文献检索
- 多人协作
- 支付系统
- LaTeX 高级排版
- 深度代码仓库分析
- 学校模板自动识别

## 10. 成功标准

MVP 完成后，应满足：

- 用户能在 30 分钟内创建一个完整论文或报告项目。
- 系统能生成可编辑大纲。
- 每个章节都有明确目的和承接关系。
- 逐章生成的内容在标题、术语和项目事实上保持一致。
- 用户能导出一份结构完整的初稿。
- 全文一致性检查能发现明显前后矛盾和重复问题。
