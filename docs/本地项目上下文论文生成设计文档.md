# 本地项目上下文论文生成设计文档

## 1. 背景与目标

当前系统已经支持从项目标题、用户填写信息和 Project Brief 出发，生成论文/课程报告大纲、章节关系、章节正文、摘要和导出文件。下一阶段需要解决一个更真实的写作场景：用户已经有一个本地软件项目，希望论文内容能够结合真实代码来写，而不是只根据标题泛化生成。

本功能的目标是建立一条稳定链路：

```text
本地项目源码
  -> 项目扫描与关键文件抽取
  -> 模块级代码分析
  -> 项目事实库 Codebase Facts
  -> 用户确认 / 编辑
  -> 写入 Project Brief 与 Material
  -> 按章节选择相关事实生成正文
```

核心原则是：读项目阶段尽可能全面，写论文阶段只携带相关事实，避免把整个源码直接塞进模型上下文。

## 2. 设计结论

推荐采用“先分析、再写作”的两阶段方案。

第一阶段为本地项目分析，系统读取目录结构、配置文件、关键源码、接口、数据库和依赖，生成结构化 Codebase Facts。

第二阶段为论文生成，系统不再直接读取完整源码，而是从 Codebase Facts 中按章节检索和裁剪上下文，再交给现有 Brief、Outline、Relation、Chapter Draft 流程使用。

不推荐每次生成章节都全量扫描项目，也不推荐把所有源码作为 related_materials 注入章节 prompt。这两种方式容易导致上下文爆炸、响应变慢、事实漂移和章节间不一致。

## 3. 用户流程

### 3.1 项目绑定

在 Project Brief 页面增加“结合本地项目写作”区域。

用户输入：

- 本地项目路径，例如 `D:\programs\shop-system`
- 项目类型提示，例如 Vue + Spring Boot、Python Web、Node.js 全栈等，可选
- 是否排除测试文件、构建产物、依赖目录
- 是否读取数据库脚本、接口文档、README

用户点击“分析本地项目”。

### 3.2 生成项目分析报告

系统返回可编辑的项目分析报告，包含：

- 项目技术栈
- 目录结构摘要
- 前端页面与路由
- 后端接口与 Controller
- Service / Repository / Mapper 结构
- 数据库表与字段
- 核心功能模块
- 关键业务流程
- 第三方依赖与外部服务
- 可写入论文的设计与实现要点
- 未能确认的信息

用户确认后，系统写入项目事实库，并同步更新 Project Brief 中的技术路线、功能模块、系统架构、开发环境和 locked_facts。

### 3.3 章节写作

生成章节时，系统按章节类型挑选事实：

```text
相关技术基础 -> 技术栈、框架依赖、关键中间件
需求分析 -> 功能模块、用户角色、业务流程
系统设计 -> 架构、模块关系、数据库设计、接口关系
系统实现 -> 前端页面、后端接口、Service、关键代码证据
测试分析 -> 运行方式、功能流程、接口用例、测试入口
总结展望 -> 已实现能力、局限、后续扩展点
```

生成后，章节摘要中记录本章使用过的项目事实，供后续章节避免重复和保持一致。

## 4. 功能范围

### 4.1 MVP 必做

- 输入本地项目路径
- 安全扫描项目文件树
- 忽略依赖目录和构建产物
- 识别常见技术栈
- 提取关键配置文件
- 提取前后端核心文件摘要
- 生成 Codebase Facts
- 用户确认后写入 Project Brief / Material
- 章节生成时按章节选择相关事实
- 一致性检查时检查正文是否违反 Codebase Facts

### 4.2 MVP 暂不做

- 完整语义索引和向量检索
- 自动运行项目
- 自动执行测试
- 自动生成 UML / Draw.io 图
- 深度跨语言调用链追踪
- 二进制文件、图片、压缩包解析
- Git 历史分析

### 4.3 后续增强

- 基于 tree-sitter 的 AST 解析
- 向量索引和章节级事实检索
- 接口调用链图谱
- 数据库 ER 图生成
- 结合 Draw.io MCP 生成论文插图
- 支持上传项目压缩包
- 支持 Git 仓库 URL 拉取分析

## 6. 后端模块设计

建议新增模块：

```text
backend/app/services/codebase_analyzer.py
backend/app/schemas/codebase.py
backend/app/api/routers/codebase.py
backend/app/ai/codebase_prompts.py
```

### 6.1 CodebaseAnalysisService

职责：

- 校验本地路径是否存在
- 检查路径是否允许访问
- 扫描项目文件树
- 按规则过滤无关文件
- 识别技术栈和项目结构
- 提取关键文件内容
- 调用 LLM 生成结构化事实
- 持久化分析结果
- 将用户确认后的事实写入 Brief 和 Materials

### 6.2 FileTreeScanner

默认忽略：

```text
.git
.idea
.vscode
node_modules
dist
build
target
.venv
venv
__pycache__
.pytest_cache
coverage
logs
*.lock
*.png
*.jpg
*.jpeg
*.gif
*.zip
*.rar
*.7z
```

输出：

```json
{
  "root": "D:/programs/shop-system",
  "total_files": 186,
  "included_files": 74,
  "tree": [
    "frontend/package.json",
    "frontend/src/router/index.ts",
    "backend/pom.xml",
    "backend/src/main/java/.../UserController.java"
  ],
  "ignored_summary": {
    "node_modules": 12600,
    "dist": 42
  }
}
```

### 6.3 TechStackDetector

通过文件和依赖识别：

- `package.json`：Vue、React、Vite、Element Plus、Pinia、Axios
- `pom.xml` / `build.gradle`：Spring Boot、MyBatis、JPA、Redis、JWT
- `pyproject.toml` / `requirements.txt`：FastAPI、Django、SQLAlchemy
- `docker-compose.yml`：MySQL、PostgreSQL、Redis、Nginx
- `application.yml` / `.env.example`：数据库、端口、外部服务

输出：

```json
{
  "frontend": ["Vue3", "Vite", "Pinia"],
  "backend": ["Spring Boot", "MyBatis"],
  "database": ["MySQL"],
  "middleware": ["Redis"],
  "deployment": ["Docker Compose"]
}
```

### 6.4 KeyFileExtractor

优先读取：

- README、接口文档、数据库脚本
- 前端路由、API client、store、主要页面
- 后端 Controller、Service、Repository / Mapper、Entity
- 数据库 migration、SQL、schema
- 配置文件

单文件读取限制建议：

```text
单文件最大 20KB
单批 LLM 输入最大 60KB
项目分析总原文预算 200KB
超限文件先做截断和摘要
```

## 7. 数据模型设计

### 7.1 新增 CodebaseAnalysis

```python
class CodebaseAnalysis:
    id: str
    project_id: str
    root_path: str
    status: Literal["pending", "running", "ready", "failed"]
    summary: str | None
    tech_stack: dict | None
    file_tree_summary: dict | None
    facts: dict | None
    missing_info: list[str] | None
    warnings: list[str] | None
    created_at: datetime
    updated_at: datetime
```

### 7.2 新增 CodebaseFact

```python
class CodebaseFact:
    id: str
    analysis_id: str
    project_id: str
    category: Literal[
        "tech_stack",
        "module",
        "api",
        "database",
        "workflow",
        "frontend",
        "backend",
        "deployment",
        "test",
        "risk"
    ]
    title: str
    content: str
    evidence_files: list[str]
    confidence: Literal["high", "medium", "low"]
    chapter_tags: list[str]
    created_at: datetime
```

### 7.3 复用 Material

确认后的分析结果同步写入 `materials`：

```text

  "analysis_id": "...",
  "root_path": "...",
  "fact_count": 36
}
```

数据库枚举中已有 `code_summary`，可以直接复用。

## 9. 上下文压缩策略

### 9.1 分层压缩

```text
源码文件
  -> 文件摘要
  -> 模块摘要
  -> 项目事实
  -> 章节上下文
```

每层都减少信息量，并保留证据文件路径。

### 9.2 Token 预算

建议预算：

```text
Codebase Facts 总量：3000-8000 中文字
单章相关项目事实：1500-4000 中文字
已完成章节：只带摘要，不带全文
关键代码证据：只带短片段或文件路径
```

### 9.3 章节事实选择规则

使用 `chapter_tags` 和章节标题匹配：

```text
绪论 -> project_overview, background, goal
相关技术基础 -> tech_stack, dependency
需求分析 -> module, workflow, role
系统设计 -> architecture, database, api
系统实现 -> frontend, backend, api, service
测试分析 -> test, workflow, deployment
总结展望 -> limitation, risk, extension
```

### 9.4 证据保留

每条事实必须保留 evidence_files。正文生成时可以不展示文件路径，但一致性检查和用户溯源需要看到依据。

示例：

```json
{
  "category": "api",
  "title": "订单创建接口",
  "content": "后端提供订单创建接口，接收购物车商品、地址和用户信息后生成订单记录。",
  "evidence_files": [
    "backend/src/main/java/.../OrderController.java",
    "backend/src/main/java/.../OrderService.java"
  ],
  "confidence": "high",
  "chapter_tags": ["系统实现", "系统设计"]
}
```

## 10. Prompt 设计

### 10.1 项目分析 Prompt

```text
你是一个软件项目分析助手。

任务：根据文件树、关键配置和关键源码摘要，生成结构化 Codebase Facts，用于后续课程报告/本科论文写作。

要求：
1. 只根据提供的文件和摘要判断，不要编造不存在的功能。
2. 每条事实必须给出 evidence_files。
3. 如果无法确认，请放入 missing_info，不要猜测。
4. 输出应偏论文可用表达，但不要直接生成论文正文。
5. 输出 JSON，不要输出 Markdown。

项目标题：{project_title}
用户提示：{user_hint}
文件树摘要：{file_tree}
技术栈初步识别：{tech_stack}
关键文件摘要：{key_file_summaries}

输出结构：
{
  "summary": "",
  "tech_stack": {},
  "facts": [
    {
      "category": "",
      "title": "",
      "content": "",
      "evidence_files": [],
      "confidence": "high | medium | low",
      "chapter_tags": []
    }
  ],
  "missing_info": [],
  "warnings": []
}
```

### 10.2 Brief 融合 Prompt

```text
你是一个论文 Project Brief 整理助手。

任务：将用户原始项目信息与 Codebase Facts 融合，生成后续写作唯一事实来源。

要求：
1. 项目中已确认的功能、技术栈、数据库和模块必须优先使用 Codebase Facts。
2. 不得加入 Codebase Facts 和用户信息中都没有的功能。
3. 如果代码事实与用户填写内容冲突，请在 missing_info 中标记。
4. locked_facts 必须包含关键技术栈、核心模块、数据库和主要流程。
5. 输出 JSON。
```

### 10.3 章节生成 Prompt 增补

在现有 `CHAPTER_DRAFT_PROMPT` 中增加：

```text
本章可使用的本地项目事实：
{codebase_facts}

代码事实使用规则：
1. 必须优先依据本地项目事实写作。
2. 不得编造项目中不存在的功能、接口、数据库表、技术栈或测试结果。
3. 如果本章需要某项信息但 codebase_facts 中没有证据，请使用“[待补充：具体信息]”。
4. 写系统设计和系统实现时，应体现模块、接口、数据库和调用流程之间的关系。
5. 不要贴大段源码，只提炼设计意图、实现流程和关键技术点。
```

## 12. 安全与权限

本地路径读取是高风险能力，必须加约束。

MVP 约束：

- 只允许读取用户显式输入的项目路径
- 后端校验路径存在且为目录
- 禁止读取系统敏感目录，如 `C:\Windows`、用户 `.ssh`、浏览器数据目录
- 默认忽略 `.env`，除非只读取 key 名不读取 value
- 默认忽略私钥、证书、token 文件
- 不读取二进制文件
- 文件大小超限自动跳过
- 分析结果里不保存密钥值

敏感文件规则：

```text
.env
.env.local
*.pem
*.key
id_rsa
id_ed25519
credentials.json
token.json
```

如果扫描发现疑似密钥，只记录：

```text
检测到敏感配置文件，已跳过内容读取。
```

## 13. 错误处理

### 13.1 路径不存在

返回：

```text
本地项目路径不存在，请检查路径是否正确。
```

### 13.2 权限不足

返回：

```text
当前进程没有权限读取该目录，请换一个项目目录或调整权限。
```

### 13.3 项目过大

处理：

- 先展示文件数量和扫描预算
- 提示用户增加忽略规则
- 允许只分析指定子目录

### 13.4 模型分析失败

处理：

- 保存文件树和技术栈检测结果
- 允许重试
- 不覆盖已有 Codebase Facts

## 14. 一致性检查增强

Consistency Review 增加检查项：

- 正文是否出现 Codebase Facts 中没有的功能模块
- 技术栈是否与项目分析结果冲突
- 数据库表名、模块名、接口名是否前后不一致
- 系统实现章节是否引用了不存在的实现细节
- 测试章节是否编造了未提供的测试结果

新增 issue 类型：

```text
codebase_fact_conflict
unsupported_feature
unsupported_tech_stack
unverified_test_result
missing_code_evidence
```

## 17. 关键风险与取舍

### 17.1 上下文过大

风险：项目文件太多，模型无法一次分析。

缓解：

- 扫描和写作分阶段
- 先摘要再合并
- 每章只带相关事实
- 设置文件数量和大小预算

### 17.2 误判项目功能

风险：模型根据文件名推断出不存在的功能。

缓解：

- 每条事实必须带 evidence_files
- confidence 分级
- 用户确认后才写入 Brief
- 一致性检查对低置信事实更谨慎

### 17.3 读取敏感信息

风险：项目中包含密钥和私有配置。

缓解：

- 默认跳过敏感文件
- 对 `.env` 只读取 key 名
- 不保存 secret value
- 页面明确提示读取范围

### 17.4 论文变成代码说明书

风险：系统实现章节过度贴近代码，缺少论文表达。

缓解：

- Prompt 要求“不贴大段源码”
- 将事实转为设计意图、实现流程和模块职责
- 相关技术章节只解释项目用到的关键技术

## 18. 推荐实现顺序

先做最小闭环：

```text
路径输入
  -> 文件树扫描
  -> 技术栈识别
  -> LLM 生成项目分析报告
  -> 用户确认
  -> 写入 Material
  -> 章节生成时附加 Material
```

这个闭环做通后，再补 CodebaseFact 表、章节事实选择、证据展示和一致性检查增强。

原因是当前系统已经有 `Material`、`ProjectContext`、`ProjectBrief` 和章节生成链路，先复用现有结构可以最快验证效果。等效果稳定，再引入更精细的数据模型。

## 19. 成功标准

功能上线后应满足：

- 用户可以在 1-3 分钟内完成中小型项目分析
- 分析报告能准确识别主要技术栈和核心模块
- 确认后生成的系统设计/实现章节明显结合真实项目
- 正文不编造项目中不存在的主要功能
- 用户可以看到每条关键事实的证据文件
- 后续章节生成不会因为项目上下文过大而失败
